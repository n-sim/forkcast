# Embed a shared Rust application core and synchronize with an optional household server

Forkcast desktop and Android installations bundle the React/TypeScript frontend and a Rust application core. The core owns application workflows, SQLite persistence and migrations, domain rules, synchronization, and AI execution. A headless self-hosted server hosts the same core implementation with HTTP and account-administration adapters. This concentrates behavior currently spread across frontend IndexedDB storage, the backend, and the AI companion, while preserving use without server administration.

Installed frontends always read and write through their embedded core, including after joining a household server. Local writes and pending synchronization work commit durably together. Devices synchronize with the server and retain offline reads, edits, cooking progress, and shopping checklists through outages and process restarts. Joining a server does not switch the installed frontend to remote-only execution. Conflict preservation, household adoption review, and ownership remain governed by ADRs 0008 and 0014. Synchronization remains necessary; sharing its implementation does not eliminate distributed-data conflicts.

Standalone installations use one persistent local person without login. Joining a server explicitly associates that person's records with the authenticated account and reviews existing household data before publishing it. Household records include recipes, meal plans, the active shopping list, and cooking occurrences; ratings, food logs, goals, AI preferences, and resumable cooking sessions remain personal. Pending changes retain their original person/account and household association across sign-out, disconnect, restart, and account changes. Rejoining the same household is resumable; another household requires a separate local profile. Cancelling adoption leaves both sides unchanged.

The shared core presents cohesive workflow operations through a small interface. Native bridges and HTTP are transport adapters; React does not own a second durable application store or reimplement mutations, synchronization, or AI orchestration. SQLite records and migrations are shared by embedded and server hosts, with explicit platform adapters for credential protection, paths, browser launch, files, and lifecycle. Hosts supply the authenticated or local person context; server authorization remains enforced independently of the UI. The embedded core starts with the app and restores persisted state after termination; Android does not require a permanently running daemon. Exact packaging tools and transport details remain implementation choices.

Browser use requires a reachable self-hosted server. The server can serve the frontend, whose operations use the server's core. A static-hosted standalone browser/PWA with its own IndexedDB implementation is no longer a product target. Browser clients do not promise offline mutations; installed apps provide that capability. Cached browser assets must not falsely report that a server-side save succeeded while disconnected.

AI remains optional. Standalone AI uses the embedded native core with protected local credentials and the documented loopback authorization flow. Connected mode uses the person's server AI connection; server failure is shown explicitly without silently switching credentials or identities. Joining a household for data synchronization does not require ChatGPT authorization. An explicit in-app server AI setup completes local sign-in and transfers the credential session directly from the native core to the authenticated server account over HTTPS, without SSH, shell commands, manual token copying, or tokens passing through React. The server retains its own host identity and becomes the sole refresh owner for the transferred session. Transfer must be acknowledged, retryable, and recoverable after interruption without concurrent refresh ownership. Tokens are runtime secrets, never ordinary synchronized settings. Browser users can use an established server AI connection; initial setup and reconnection require an installed app under the documented flow. See [OpenAI remote setup](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms) and [session protection](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions). Android authorization and lifecycle support require physical-device validation before claiming release readiness.

Migration must preserve existing browser data through an explicit, repeatable transfer into the installed core, and upgrade existing server databases without losing identities, retained nutrition, assets, conflicts, or pending work. Existing AI runtime credentials need a protected native migration or an explicit reconnection path; credential files must not enter the browser data transfer. Source data is retained until destination verification succeeds. Existing browser data is not assumed to be accessible from an installed app's origin. The old browser store and separate companion are transitional implementations, retired only after migration and equivalent workflow verification.

This decision supersedes ADRs 0002 and 0012 and replaces the companion packaging and manual remote-credential setup in ADR 0010. Server-backed backups remain in scope; general standalone backup/restore remains outside the current product scope. The GitHub product specification and migration tickets describe implementation status and acceptance criteria; this decision records the target architecture, not completed implementation.
